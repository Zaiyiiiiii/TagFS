# TagFS 架构设计（草案）

本文定义 TagFS 的分层、数据模型、可见性规则、查询、存储格式和工程划分。标“建议”的地方是本草案提出的方案，待确认；第 10 节记录已经定下的决定和后做的事项。

## 0. 定位与原则

TagFS 是一个独立工程，是操作系统原生的文件系统，用 Rust 实现。

- **只服务操作系统本身。** 调用方是操作系统内核及其运行时（handler），不面向任何其他系统，也不为别的组件妥协。
- **反 POSIX。** 没有路径、目录、文件名、inode、rwx 权限位、链接。不提供 POSIX 语义，也不以兼容为设计约束。
- **兼容层不属于本工程。** 将来如果需要面向路径世界的兼容层，它在 TagFS 之外单独实现，只使用 TagFS 的公开接口，不得反向影响 TagFS 的模型。
- **完整实现。** 从实体模型到磁盘格式、事务、崩溃恢复、空间回收都由本工程负责，不寄生在其他文件系统之上。宿主机文件和目录只是存储后端，里面存的是 TagFS 自己的格式和语义。

几条贯穿全局的规则：

1. 实体身份独立于一切描述：改 Tag、改内容都不改变身份。
2. 名称只是 Tag，没有特殊地位。
3. 调用者只操作实体（带 Tag 的引用），对象（内容）由系统自动管理，没有人直接删除对象。
4. 单设备还是多设备，对读写实体的调用者没有区别。
5. 权限就是 Tag。对调用者没有读取权限的实体，在它看来不存在，所有接口都表现一致。
6. Tag 由调用上下文自动注入，调用者只写条件，不接触安全上下文。
7. 逻辑层和物理映射层彻底分离：物理映射只认存储层自己的标识，不知道 Tag 是什么。

## 1. 分层总览

```
操作系统（内核 / handler 运行时）
   │  调用 TagFS API，并传入可信调用上下文
   ▼
┌──────────────────────────────────────────────┐
│ API 层：卷、事务、实体读写、Tag 读写、查询     │
├──────────────────────────────────────────────┤
│ 逻辑层：实体 · Tag · 可见性 · 查询规划与合并    │
├──────────────────────────────────────────────┤
│ 卷层：多个存储单元组成一个卷，单元可在线/离线    │
├──────────────────────────────────────────────┤
│ 存储单元接口：每个单元自管元数据、索引、对象     │
└──────────────────────────────────────────────┘
   │
   ▼
存储后端：块格式（宿主机单文件 / 裸盘 / 内存）· 宿主机目录 · 将来的裸机驱动
```

每层只依赖下一层的接口。逻辑层不知道有几个存储单元、它们怎么存；存储后端不知道 Tag 的语义。

## 2. 数据模型

TagFS 里有两种东西：调用者操作的**实体**，和系统管理的**对象**。

### 2.1 实体

实体就是“含 Tag 的引用”，是调用者能看到、能操作的唯一的东西。它有：

- **EntityId**：128 位，创建时生成，全局唯一，永不复用。建议按 UUIDv7 生成（带时间序，索引局部性好）。存储单元内部另用 64 位本地编号做索引键，两者的映射只存在于存储单元内。
- **对象引用**：指向一个对象（见 2.4）。
- **Tag 集合**：实体的全部描述，包括名称、类型、归属、权限边界。

实体本身没有名字、类型、父目录、时间戳这些固定字段，需要的都表达成 Tag。调用者可以创建、读写、删除实体。

### 2.2 Tag

一个 Tag 是 `(命名空间, 键, 值)`。

**命名空间**决定谁能写、谁来解释。TagFS 自己只定义一个命名空间：

- **`tagfs`**：只有 TagFS 自己写入，任何调用者（包括操作系统）都不能写。用于 TagFS 自身的状态，例如未完成事务标记 `tagfs:txn_pending`、实体所在的单元。

其余所有命名空间都由上层定义，TagFS 不知道它们的含义，只把命名空间当作不透明的名字。例如操作系统可以定义：

| 命名空间（举例） | 由谁定义 | 用途举例 |
|---|---|---|
| `system` | 操作系统 | 实体归属用户、归属应用、安装状态 |
| 每个应用一个，以 AppId 区分 | 操作系统分配，应用使用 | 应用自己的语义，如播放列表 |
| 用户 | 操作系统 | 名称、项目、用途等自定义描述 |

这些名字、它们怎么书写、谁能写，都是操作系统的事。文档里出现的 `system:owner_app` 之类只是举例。

**值的类型**只有三种：

- **无值**：只表示这个 Tag 存在。
- **uint**：无符号整数（64 位），按数值比较和排序。
- **字符串**：UTF-8，按字节比较和排序。

没有数组类型。需要多个值时就打多个 Tag：同一个实体上，同一命名空间下的同一个键可以出现多次，每次一个值。

长度上限：命名空间名和键各 64 字节，字符串值 4096 字节（和 Linux 的 `PATH_MAX` 一样）。Tag 要整体放进索引键，所以必须有上限；更长的内容应当放进实体本身。

**名称**就是一个普通 Tag（用哪个命名空间、哪个键由上层定）：可以重复、可以没有、可以有多个。TagFS 不知道哪个 Tag 是“名称”。

### 2.3 关系

TagFS 没有专门的关系类型。实体之间的关系就是值为另一个实体 EntityId（字符串形式）的普通 Tag，例如上层定义的 `derived_from = "<EntityId>"`。

- 关系和其他描述走同一套写入规则、查询和可见性规则，不另设机制。
- “哪些实体引用了 X”就是查询 `键 = "X 的 EntityId"`，用普通的 Tag 索引即可，不需要反向索引。
- TagFS 不解释这个值。按值去取目标实体时，目标对调用者不可见或所在单元离线，就和不存在一样（见 3.3、5.1）。

### 2.4 对象

对象是一段字节，是实体背后的内容，由系统自动管理：

- 一个实体引用一个对象，多个实体可以引用同一个对象。
- 没有删除对象的操作。删除实体时同步检查它引用的对象是否还有别的实体引用，没有就回收。
- 对象按写时复制处理：通过某个实体修改内容时，如果对象还被别的实体引用，就产生新对象，只有这个实体指向新对象，其他实体不受影响。

由此区分两种操作：

- **复制**：创建一个新实体，有新的 EntityId、自己的 Tag 集合，和原实体引用同一个对象，直到任一方修改内容。
- **添加语义**：给同一个实体加 Tag，身份、内容都不变。

## 3. 调用上下文与可见性

### 3.1 可信调用上下文

每次调用都带一个上下文，由操作系统构造并传入，调用者（应用）不能直接构造或修改：

- 主体 Tag：当前用户、当前应用的 AppId、所属组等。
- 已授予的能力：操作系统经 manifest 申请、用户批准后授予的条目。

TagFS 不做身份认证，它信任调用它的操作系统传来的上下文。信任边界就在 API 入口：TagFS 的 API 只对操作系统开放，应用通过操作系统间接调用。

### 3.2 边界

操作系统可以把某些 Tag 注册为**边界 Tag**，例如它定义的 `system:owner_user`、`system:owner_app`、`system:tenant`。每一种边界有一条规则，说明主体满足什么条件才能越过这道边界。哪些 Tag 是边界、规则是什么，TagFS 都不预设。

- 实体可见，当且仅当它身上出现的每一种边界都被主体满足（各边界取交集，任一不满足即不可见）。
- 边界的种类和规则由操作系统在挂载卷时注册，TagFS 负责执行。这样用户隔离、应用隔离、租户隔离都是同一机制的不同实例，不写死在 TagFS 里。
- 能力只能放宽它针对的那一种边界。例如“读取所有用户文件”的能力放宽用户边界，但不放宽应用边界：带 `system:owner_app = notepad` 的实体，即使调用者有全盘读取能力，只要不是 notepad，仍然不可见。要让它对外可见，只能由有权的一方去掉这个边界 Tag。

### 3.3 不可见即不存在

读权限决定实体是否存在于调用者的世界里。对不可见的实体，所有接口都表现得和它从未存在一样：

- 按 EntityId 获取：返回“不存在”，和真的不存在是同一个错误。
- 查询、计数、分页：不计入，不影响结果数量和顺序。
- 错误信息：读路径上没有“权限不足”这种错误。

写入另有规则：实体可见但不可写时返回“只读”。这不泄露任何信息，因为实体本来就可见。

内部审计可以区分“不存在”和“不可见”，但这个区分只出现在只对操作系统开放的接口里。

### 3.4 写入规则

- `tagfs` 命名空间只能由 TagFS 自己写入，任何调用者（包括操作系统）都不能写。
- 其他命名空间的写入规则由操作系统在挂载卷时注册，和边界规则（3.2）是同一机制：每个命名空间一条规则，说明主体满足什么条件才能写。TagFS 只负责执行。例如“`system` 只能由带相应能力的上下文写”“某个应用的命名空间只能由该应用写”，都是操作系统注册的规则。
- 没有注册规则的命名空间，默认任何可见该实体的调用者都不能写（默认拒绝）。
- 创建实体时附加哪些归属类的边界 Tag，由操作系统决定，调用者不能省略也不能伪造。

## 4. 查询

### 4.1 表达

查询在核心里是结构化的表达式树，没有字符串语法：

- 谓词：键存在、等于、范围（uint、字符串）、前缀（字符串）。
- 组合：与、或、非。
- 结果：EntityId 列表，支持排序键和分页游标。

沿关系查找就是两步普通查询：先取出某个键的值，再按这些 EntityId 去取。

调用者写的只是条件。可见性规则由执行器自动并入，调用者既不需要、也无法在查询里写权限条件。

### 4.2 执行

- 卷层把查询分发给每个在线的存储单元，各单元在自己的索引上执行，结果在逻辑层合并、排序、分页。离线的单元不参与，它上面的实体不出现在结果里。
- 单元内的规划器根据各谓词的选择性挑选索引，先算候选集，再做交、并、差。
- 可见性作为一个强制谓词参与规划。边界 Tag 本身也有索引，可以先用它缩小候选集。比如音乐应用查 `playlist = ilike`，规划器可以先取 `system:owner_app = music` 的集合再求交；调用者有全盘权限时，规划器换成按 Tag 索引直接查。
- 规划只影响执行顺序，不能改变结果：无论走哪条索引，结果都满足全部谓词和可见性。

### 4.3 索引

每个存储单元只为自己的实体维护：

- 实体表：EntityId → 实体记录（对象引用、Tag 集合）。
- Tag 倒排索引：（命名空间, 键, 值）→ 实体集合。所有 Tag 都进索引，不需要预先声明。
- 对象引用计数：对象 → 引用它的实体数。

没有跨单元的全局索引。建议首版所有 Tag 一律索引，等有实测数据再优化。

## 5. 卷与存储单元

### 5.1 卷

一个卷由一个或多个存储单元组成（一块盘、一个宿主机文件、一个宿主机目录都是一个单元）。对调用者来说，单单元和多单元没有区别：读写实体的接口一样，实体全局唯一。

- **每个单元只负责自己的元数据。** 实体、它的 Tag、它引用的对象、对应的索引都存在同一个单元里，单元之间不互相保存对方的任何数据。
- **单元离线，它的元数据就离线。** 它上面的实体从卷里消失：查询不到，按 EntityId 取不到，和不存在一样；单元重新上线，它们随之回来。不需要单独的“离线”状态或错误。
- **新实体放在哪个单元**由卷的分配策略决定，对调用者透明。建议默认策略：优先写入最快的单元，低于剩余空间阈值时转到下一个。操作系统也可以在创建时指定单元。
- 实体所在的单元可以作为 `tagfs` Tag 暴露给操作系统，用于管理界面。
- 一个实体和它引用的对象总在同一个单元。跨单元复制就是在目标单元里创建新实体和新对象。

### 5.2 块格式单元的元数据结构

以下 5.2 到 5.5 是块格式单元（宿主机单文件、裸盘、内存）的实现。宿主机目录单元的实现见第 6 节。

每个单元开头有超级块（两份，交替写），记录卷标识、单元标识、格式版本、当前提交的根位置。

使用一棵写时复制的 B+ 树存放这个单元的全部元数据：实体表、实体的 Tag、Tag 索引、对象记录（引用计数、长度、内联内容）、对象的区段映射、准备记录、已提交事务。键的第一个字节区分种类，其余字段用保序编码（整数大端，字符串转义后定界），所以同一前缀的条目在树里相邻，范围和前缀查询就是一次顺序扫描。具体布局见 `crates/tagfs-block/src/keys.rs`。

块大小至少 4096 字节。节点通常占一个块；单个条目本身超过一块时（例如接近上限的长 Tag），它独占一个节点，这个节点跨多个不必连续的块存放，第一块记着其余块的位置。所以长 Tag 只是多占几个块，不需要连续空间，也不影响普通节点的读写。

空闲空间不在树里，而是每次提交整份写成一条空闲表（块链），由超级块指向。这样分配块不会反过来修改树。代价是每次提交都要重写空闲表，碎片多时开销随区段数增长；以后可以换成增量的形式。

- 修改永远写到新位置，提交时原子地切换超级块里的根指针。断电后，要么看到旧的根，要么看到新的根，不会出现半成品。
- 不需要单独的日志来保证一致性，这是选它而不选“原地更新加日志”的主要原因。
- 每个节点带校验和和所属的提交号，读取时校验。
- 天然支持只读快照：保留旧的根即可，这让并发读取不必加锁（见 7.2）。

### 5.3 对象映射与空间分配

- 对象映射：（对象标识, 逻辑块号）→（物理块号, 块数）。这一层只认对象标识，不知道引用它的实体和 Tag。没有映射的逻辑块是空洞，读出来是零，所以变长不需要写零。
- 不超过 512 字节的对象内联在 B+ 树的叶节点里，不单独分配块。
- 空间按区段分配，尽量为一个对象分配连续的块。写内容时，被改到的块写到新位置，原来的块释放，已提交的状态不受影响。
- 被共享的对象（复制出来、还没改过的）被修改时先整份复制一个给修改方。
- 释放的块要在这次提交之后、并且引用旧根的读者都结束之后，才能重新分配。

### 5.4 事务

- API 层的一个事务把多个操作（建实体、写内容、改 Tag、删实体）合成一次提交，要么全部生效，要么全部不生效。一个事务可以涉及多个单元（例如跨单元复制），在逻辑层仍然是一个原子操作。
- 每个单元同一时刻只有一个写事务，其他写事务排队。读取在提交好的快照上进行，不阻塞写。

**只涉及一个单元**：先把数据块和新的树节点写入并刷盘，再写超级块切换根并刷盘。切换超级块就是提交点。

**涉及多个单元**：由逻辑层协调两阶段提交，其中一个参与单元指定为主单元。

事务没有在所有参与单元上完成之前，它涉及的每个实体都带一个 Tag `tagfs:txn_pending = "<事务编号>"`。这个 Tag 就是“未完成事务”的标记，单元本身照常在线。

1. **准备**：每个参与单元把一条准备记录作为一次单单元提交写下。准备记录包括事务编号、全部参与单元、主单元，以及这个单元要做的逻辑修改（其中给涉及的实体加上 `tagfs:txn_pending`）。这时各单元里的实体都还没变。之后应用准备记录时，同一次单单元提交里删掉这条记录。
2. **提交点**：主单元在一次提交里应用自己的准备记录，同时在树里记下“事务已提交”。这一步完成，事务就算提交了。
3. **完成**：其他参与单元各自应用准备记录。全部参与单元都完成之后，各单元在下一次提交里去掉这些实体上的 `tagfs:txn_pending`，主单元清掉“已提交”记录。

崩溃或断电后，带着准备记录的单元在挂载时向主单元查询这个事务：主单元记录了已提交，就应用准备记录；主单元没有提交，就丢弃准备记录。主单元自己的状态由它的超级块决定，不需要问别人。

准备记录存的是逻辑修改而不是现成的新根，所以准备之后单元还能照常接受别的提交。已知的不足：应用准备记录时仍可能因为空间不够而失败（准备阶段没有预留空间），这时事务停在“未完成”，涉及的实体保持只读，直到腾出空间后再次恢复；另外，跨单元复制的内容会整份放进准备记录，暂时占用树的空间。

**主单元不在线时**，带准备记录的单元照常上线，用的是提交前的根，只是在这个事务涉及的、已经存在的实体上打上 `tagfs:txn_pending`（这本身是一次单单元提交）。事务里新建的实体在结果确定之前不出现。等主单元可以查询时：

- 主单元已提交：把准备好的改动应用上，去掉 `tagfs:txn_pending`。
- 主单元没有提交：直接去掉 `tagfs:txn_pending`，丢弃准备记录。

带 `tagfs:txn_pending` 的实体在事务结果确定之前只读，保证之后应用改动时不会和别的写入冲突。

`tagfs:txn_pending` 是普通的 Tag，所以可以照常查询（例如找出所有未完成事务涉及的实体）；它对调用者是否可见、怎样呈现，由操作系统按 3.2 的边界规则决定。

**读取的一致性**：读者在卷级别取快照，同时拿到所有单元的根。一次多单元提交在第 3 步的切换全部完成之前，新的读者拿到的仍是提交前的那组根，所以正常情况下读者不会看到只有一部分单元提交了的事务。只有参与单元离线造成事务停在中途时，才会看到一部分已提交的实体，而这些实体都带着 `tagfs:txn_pending`。

### 5.5 空间回收

- 删除实体，或实体改为引用新对象时，在同一个事务里把旧对象的引用计数减一；减到零，对象的区段在这次提交里释放。
- 树节点在不再被当前根引用、也没有读者持有旧快照时回收。

## 6. 存储后端

卷层面对的是存储单元接口：单元负责自己的实体、Tag、对象、索引、事务和回收。不同的后端各自实现这个接口，一个卷里可以同时有多种后端的单元。

**块格式后端**：用第 5 节的格式，存在任何实现了 `BlockDevice` 的设备上。

```rust
pub trait BlockDevice {
    /// 设备的物理块大小；分配按它对齐
    fn block_size(&self) -> u32;
    fn capacity(&self) -> u64;
    /// 任意偏移、任意长度；对齐要求由实现自己消化
    fn read_at(&self, offset: u64, buf: &mut [u8]) -> Result<(), DeviceError>;
    fn write_at(&mut self, offset: u64, buf: &[u8]) -> Result<(), DeviceError>;
    /// 返回时，之前的写入已经持久化
    fn flush(&mut self) -> Result<(), DeviceError>;
    fn trim(&mut self, offset: u64, len: u64) -> Result<(), DeviceError>;
}
```

- 设备实现：内存（测试、临时卷）、单文件（镜像文件，放在宿主能访问的任何地方）、各平台裸盘、将来的裸机块驱动。
- 块缓存放在设备之上，所有设备实现共用。

**目录后端（POSIX、Windows）**：目的是让操作系统和应用层能读写宿主上按路径组织的文件。

- 挂载目录就是根 `/`，挂载目录之上的路径不会出现在 Tag 里。目录里的每个普通文件是一个实体，带 `tagfs:hostfs_path`（层级文件系统路径），值形如 `/abc/bcd/1.file`；内容就是那个文件，不复制。目录不是实体。
- `tagfs:hostfs_path` 是映射的 Tag，不是存储的 Tag：加上它就在宿主上建出文件（缺的上层目录同步建出），改它就移动文件，去掉它或删除实体就删除宿主文件。上层改它按“修改实体”授权。
- 没有这个 Tag 的实体存在挂载目录下的镜像文件里（`/.tagfs/unit.img`，块格式）。镜像文件同时存放全部实体的 Tag 和索引，以及目录单元自己的记录。`/.tagfs` 是保留名。
- 防护：路径值必须以 `/` 开头、没有空段、`.`、`..`、NUL，每段都是宿主上合法的文件名，长度不超过 Tag 上限；路径上的每一级都不能是符号链接。所以映射路径永远落在挂载目录里。扫描时不跟随符号链接，也不映射它们。
- 一次修改分两步提交：先在镜像里提交实体的修改和要做的宿主操作（意图记录），这是提交点；再操作宿主（先把要让出的文件挪进 `/.tagfs/tmp`，新内容写临时文件后改名到位）；最后在镜像里清掉意图记录。中途断电，挂载时按意图记录做完。要读写内容的路径实体，先把宿主文件的内容搬进镜像，改完再写回。
- 挂载时扫描整个目录和镜像对账：新文件建成实体，消失的删掉，改了名的（POSIX 上按 inode 加创建时间识别）更新路径、保持实体不变。
- 路径实体的内容是宿主文件的当前内容，不受快照保护，宿主上的程序随时可能改它。

已知的不足：写路径实体的内容时整个文件要过一遍内存；Windows 上暂时不识别宿主侧的改名（当作删除加新建）；宿主文件系统不报告创建时间时，inode 被复用可能被误认成改名。

错误码统一定义，不把宿主的 errno 带进核心。

## 7. API 层

### 7.1 形态

TagFS 以 Rust 库的形式交付给操作系统，接口大致是：

- 卷：创建、挂载（注册边界规则）、卸载、加入或移除存储单元、单元上线和离线。
- 事务：开始、提交、放弃。
- 实体：创建、按 EntityId 获取、删除、复制。没有对象级的操作。
- 内容：通过实体按偏移读、写、截断，读取长度。
- Tag：增加、删除、列出（只列出可见的命名空间）。
- 查询：执行表达式，返回游标。

操作系统怎样把这些接口转给应用（handler、IPC 或其他方式）是操作系统的事，不在本工程内。

### 7.2 并发

- 读取在快照上进行，多个读者互不阻塞，也不阻塞写者。
- 写事务串行。是否支持多个写事务并发提交，留到有实测需求时再定。

Cargo workspace：

| crate | 内容 | 依赖 |
|---|---|---|
| `tagfs-core` | 实体、Tag、查询表达式、可见性规则、查询规划与合并、卷、存储单元接口 | `no_std` + `alloc` |

测试从一开始就包括故障注入：在任意一次设备写入后模拟断电，重新挂载，检查卷一致、已提交的事务完整、未提交的事务不留痕迹。

## 9. 明确不做的

- 路径、目录、当前目录、相对位置。
- 硬链接、符号链接、挂载点。
- rwx 权限位、属主/属组、ACL。
- 任何 POSIX 或 Win32 文件语义，以及 FUSE、WinFsp 之类的挂载适配。
- 读取外部路径型文件系统（FAT、NTFS、ext4 等）。需要的话属于兼容层。
- 对象的历史版本。保存历史不是文件系统的职责。
- 删除对象的操作。对象由系统按引用自动回收。

## 10. 已定的决定与后做的事项

已定：

1. **单设备和多设备没有区别。** 读写实体的接口天然覆盖单个或多个存储单元，这是模型本身的一部分，不是后加的功能（5.1）。
2. **每个单元只管自己的元数据。** 不在各单元之间冗余保存；单元离线，它的元数据和实体一起离线（5.1）。
3. **不保存历史版本。** 不是文件系统的职责（第 9 节）。
4. **Tag 值类型只有无值、uint、字符串**，没有数组，多个值就打多个 Tag（2.2）。
5. **没有删除对象的操作。** 调用者只操作实体；删除实体时同步检查对象是否还有引用，没有就回收（2.4、5.5）。
6. **存储后端可以有多种**：宿主机单文件、宿主机目录、裸盘、内存，一个卷里可以同时有（第 6 节）。
7. **实体和它引用的对象必须在同一个单元**，不允许分开存放。所以不存在"实体在、内容离线"的状态；跨单元复制就是在目标单元里新建实体和对象（5.1）。
8. **跨单元的操作也是一个原子操作**，由逻辑层协调两阶段提交（5.4）。事务停在中途时不让整个单元离线，而是给涉及的实体打上未完成事务的 Tag `tagfs:txn_pending`，结果确定后再去掉。
9. **TagFS 只定义 `tagfs` 命名空间。** 其他命名空间、它们的写入规则和边界规则都由操作系统定义和注册；没有注册写入规则的命名空间默认谁都不能写（3.4）。
