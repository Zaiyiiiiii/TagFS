# TagFS 架构设计（草案）

本文定义 TagFS 的分层、数据模型、可见性规则、查询、存储格式和工程划分。标“建议”的地方是本草案提出的方案，待确认；第 10 节列出需要决定的问题。

## 0. 定位与原则

TagFS 是一个独立工程，是操作系统原生的文件系统，用 Rust 实现。

- **只服务操作系统本身。** 调用方是操作系统内核及其运行时（handler），不面向任何其他系统，也不为别的组件妥协。
- **反 POSIX。** 没有路径、目录、文件名、inode、rwx 权限位、链接。不提供 POSIX 语义，也不以兼容为设计约束。
- **兼容层不属于本工程。** 将来如果需要面向路径世界的兼容层，它在 TagFS 之外单独实现，只使用 TagFS 的公开接口，不得反向影响 TagFS 的模型。
- **完整实现。** 从对象模型到磁盘格式、事务、崩溃恢复、空间回收都由本工程负责，不寄生在其他文件系统之上。宿主机文件只是众多块设备之一，存的是 TagFS 自己的格式。

几条贯穿全局的规则：

1. 对象身份独立于一切描述：改 Tag、改内容、迁移物理位置都不改变身份。
2. 名称只是 Tag，没有特殊地位。
3. 权限就是 Tag。对调用者没有读取权限的对象，在它看来不存在，所有接口都表现一致。
4. Tag 由调用上下文自动注入，调用者只写条件，不接触安全上下文。
5. 逻辑层和物理映射层彻底分离：存储层只认存储层自己的标识，不知道对象、Tag 是什么。

## 1. 分层总览

```
操作系统（内核 / handler 运行时）
   │  调用 TagFS API，并传入可信调用上下文
   ▼
┌──────────────────────────────────────────────┐
│ API 层：卷、事务、对象读写、Tag 读写、查询     │
├──────────────────────────────────────────────┤
│ 逻辑层：对象 · Tag · 关系 · 可见性 · 查询规划   │
├──────────────────────────────────────────────┤
│ 存储层：元数据树 · 索引 · 内容映射 · 空间分配   │
│        事务提交 · 崩溃恢复 · 空间回收 · 多设备 │
├──────────────────────────────────────────────┤
│ 设备层：BlockDevice 接口（按字节偏移读写）     │
└──────────────────────────────────────────────┘
   │
   ▼
设备实现：内存 / 宿主机单文件 / 裸盘 / 将来的裸机驱动
```

每层只依赖下一层的接口。逻辑层不知道磁盘布局，存储层不知道 Tag 的语义，设备层不知道任何文件系统概念。

## 2. 数据模型

### 2.1 对象

对象是 TagFS 里唯一的“东西”，它有：

- **ObjectId**：128 位，创建时生成，永不复用。建议按 UUIDv7 生成（带时间序，索引局部性好）。存储层内部另用 64 位本地编号做索引键，两者的映射只存在于存储层。
- **内容引用**：指向一份内容（见 2.4），可以为空。
- **Tag 集合**：对象的全部描述，包括名称、类型、归属、权限边界、关系。

对象本身没有名字、类型、父目录、时间戳这些固定字段，需要的都表达成 Tag。

### 2.2 Tag

一个 Tag 是 `(命名空间, 键, 值)`。

**命名空间**决定谁能写、谁来解释：

| 命名空间 | 写入者 | 用途举例 |
|---|---|---|
| 系统 `s` | 只有操作系统（通过可信上下文） | 对象归属用户、归属应用、设备、安装状态 |
| 应用 `a:<AppId>` | 该应用 | 应用自己定义的语义，如播放列表 |
| 用户 `u` | 用户及其授权的应用 | 名称、项目、用途等自定义描述 |

- 应用命名空间以系统分配的 AppId 为限定，两个应用都定义 `playlist` 也互不冲突。AppId 由操作系统分配和维护（更新时保持不变），TagFS 只把它当作不透明的标识。
- 命名空间的书写规则（你提到的“用户定义的必须是双长度，与系统的区分开”）在 API 层用结构化类型表达，核心不解析字符串。字符串语法属于上层，见第 10 节。

**值的类型**（建议首版）：字符串、有符号整数、无符号整数、布尔、时间戳、字节串、对象引用。类型决定比较和排序规则；同一个键在同一命名空间下可以有多个值。

**名称**就是 `u:name` 这样的普通 Tag：可以重复、可以没有、可以有多个。

### 2.3 关系

关系表达为值类型是“对象引用”的 Tag，例如 `u:derived_from = <ObjectId>`、`a:<music>:in_playlist = <ObjectId>`。

- 这样关系和其他描述走同一套写入规则、同一套查询和可见性规则，不另设一套机制。
- 存储层为对象引用类型的 Tag 维护反向索引，支持“哪些对象引用了 X”。
- 引用的目标对调用者不可见时，这条关系对它也不可见（见 3.3）。

### 2.4 内容

内容是一段字节，独立于对象存在，由存储层管理：

- 一个对象引用一份内容。多个对象可以引用同一份内容。
- 内容按写时复制处理：通过某个对象修改内容，产生新的内容，只有这个对象指向新内容，其他引用者不受影响。
- 内容的引用计数归零后由空间回收释放。

由此区分两种操作，对应你在对话里的结论：

- **复制**：创建一个新对象，有新的 ObjectId、自己的 Tag 集合，内容与原对象共享，直到任一方修改。
- **添加语义**：给同一个对象加 Tag，身份、内容都不变。

## 3. 调用上下文与可见性

### 3.1 可信调用上下文

每次调用都带一个上下文，由操作系统构造并传入，调用者（应用）不能直接构造或修改：

- 主体 Tag：当前用户、当前应用的 AppId、所属组等。
- 已授予的能力：操作系统经 manifest 申请、用户批准后授予的条目。

TagFS 不做身份认证，它信任调用它的操作系统传来的上下文。信任边界就在 API 入口：TagFS 的 API 只对操作系统开放，应用通过操作系统间接调用。

### 3.2 边界

对象上的部分系统 Tag 是**边界 Tag**，例如 `s:owner_user`、`s:owner_app`、`s:tenant`。每一种边界有一条规则，说明主体满足什么条件才能越过这道边界。

- 对象可见，当且仅当它身上出现的每一种边界都被主体满足（各边界取交集，任一不满足即不可见）。
- 边界的种类和规则由操作系统在挂载卷时注册，TagFS 负责执行。这样用户隔离、应用隔离、租户隔离都是同一机制的不同实例，不写死在 TagFS 里。
- 能力只能放宽它针对的那一种边界。例如“读取所有用户文件”的能力放宽用户边界，但不放宽应用边界：带 `s:owner_app = notepad` 的对象，即使调用者有全盘读取能力，只要不是 notepad，仍然不可见。要让它对外可见，只能由有权的一方去掉这个边界 Tag。

### 3.3 不可见即不存在

读权限决定对象是否存在于调用者的世界里。对不可见的对象，所有接口都表现得和它从未存在一样：

- 按 ObjectId 获取：返回“不存在”，和真的不存在是同一个错误。
- 查询、计数、分页：不计入，不影响结果数量和顺序。
- 关系：指向它的引用 Tag、它指向别处的引用 Tag，对调用者都不可见。
- 错误信息：读路径上没有“权限不足”这种错误。

写入另有规则：对象可见但不可写时返回“只读”。这不泄露任何信息，因为对象本来就可见。

内部审计可以区分“不存在”和“不可见”，但这个区分只出现在只对操作系统开放的接口里。

### 3.4 写入规则

- `s` 命名空间只能由带相应能力的上下文写入。
- `a:<AppId>` 只能由该应用或被授予权限的主体写入。
- 创建对象时，操作系统按上下文自动附加归属类的边界 Tag，调用者不能省略也不能伪造。

## 4. 查询

### 4.1 表达

查询在核心里是结构化的表达式树，没有字符串语法：

- 谓词：键存在、等于、范围（有序类型）、前缀（字符串、字节串）。
- 组合：与、或、非。
- 关系：沿某个引用键前进或反向，带深度上限。
- 结果：ObjectId 列表，支持排序键和分页游标。

调用者写的只是条件。可见性规则由执行器自动并入，调用者既不需要、也无法在查询里写权限条件。

### 4.2 执行

- 规划器根据各谓词的选择性挑选索引，先算候选集，再做交、并、差。
- 可见性作为一个强制谓词参与规划。边界 Tag 本身也有索引，可以先用它缩小候选集。比如音乐应用查 `playlist = ilike`，规划器可以先取 `s:owner_app = music` 的集合再求交；调用者有全盘权限时，规划器换成按 Tag 索引直接查。
- 规划只影响执行顺序，不能改变结果：无论走哪条索引，结果都满足全部谓词和可见性。

### 4.3 索引

存储层维护：

- 对象表：ObjectId → 对象记录。
- Tag 倒排索引：（命名空间, 键, 值）→ 对象集合。所有 Tag 都进索引，不需要预先声明。
- 反向引用索引：目标 ObjectId → 引用它的（对象, 键）。

建议首版所有 Tag 一律索引，不做“冷 Tag 跟着对象走”的分层，等有实测数据再优化。

## 5. 存储层

### 5.1 卷

一个卷由一个或多个设备组成，所有设备构成一个全局对象空间：对象只有一个身份，不属于某块盘。

- 每个设备开头有超级块（两份，交替写），记录卷标识、设备序号、格式版本、当前提交的根位置。
- 对象的内容落在哪个设备由分配策略决定，对逻辑层透明。建议默认策略：优先写入最快的设备，低于剩余空间阈值时转到下一块。
- 内容所在的设备记录在存储层的内容映射里，必要时可作为系统 Tag 暴露给操作系统，用于管理界面。

### 5.2 元数据结构

建议使用写时复制的 B+ 树存放全部元数据：对象表、Tag 索引、反向引用索引、内容映射、空闲空间。

- 修改永远写到新位置，提交时原子地切换超级块里的根指针。断电后，要么看到旧的根，要么看到新的根，不会出现半成品。
- 不需要单独的日志来保证一致性，这是选它而不选“原地更新加日志”的主要原因。
- 每个节点带校验和和所属的提交号，读取时校验。
- 天然支持只读快照：保留旧的根即可，这让并发读取不必加锁（见 7.2）。

### 5.3 内容映射与空间分配

- 内容映射：内容标识 → 区段列表（设备, 起始块, 块数）。存储层只认自己的内容标识，不知道上面挂着哪些对象。
- 小内容内联在 B+ 树的叶节点里，不单独分配块。
- 空间按区段分配，尽量为一份内容分配连续的块。空闲空间本身也是一棵写时复制的树，随提交一起切换。
- 释放的块要等引用旧根的读者都结束、旧根不再保留之后，才能重新分配。

### 5.4 事务

- API 层的一个事务把多个操作（建对象、写内容、改 Tag）合成一次提交，要么全部生效，要么全部不生效。
- 同一时刻只有一个写事务，其他写事务排队。读取在提交好的快照上进行，不阻塞写。
- 提交时先把数据块和新的树节点写入并刷盘，再写超级块并刷盘。

### 5.5 空间回收

- 内容按引用计数回收。对象删除或改指新内容时，计数减一。
- 树节点和区段在不再被任何保留的根引用时回收。

### 5.6 设备离线

设备离线时，对象的身份和 Tag 仍在（元数据在其他设备上有副本，见第 10 节），只是内容读不到。这时读内容返回“设备离线”。这和“不存在”是两回事：对象本来就可见，告诉调用者它离线不泄露任何信息。

## 6. 设备层

```rust
pub trait BlockDevice {
    /// 设备的物理块大小；存储层按它对齐分配
    fn block_size(&self) -> u32;
    fn len(&self) -> u64;
    /// 任意偏移、任意长度；对齐要求由实现自己消化
    fn read_at(&self, offset: u64, buf: &mut [u8]) -> Result<(), DeviceError>;
    fn write_at(&self, offset: u64, buf: &[u8]) -> Result<(), DeviceError>;
    /// 返回时，之前的写入已经持久化
    fn flush(&self) -> Result<(), DeviceError>;
    fn trim(&self, offset: u64, len: u64) -> Result<(), DeviceError>;
}
```

- 错误码统一定义，不把宿主的 errno 带进核心。
- 实现：内存（测试、临时卷）、宿主机单文件（当前在宿主上运行的主要形态）、各平台裸盘、将来的裸机块驱动。
- 存储层自己做块缓存，放在设备层之上，所有设备实现共用。

## 7. API 层

### 7.1 形态

TagFS 以 Rust 库的形式交付给操作系统，接口大致是：

- 卷：创建（格式化）、挂载（注册边界规则）、卸载、加入或移除设备。
- 事务：开始、提交、放弃。
- 对象：创建、按 ObjectId 获取、删除、复制。
- 内容：按偏移读、写、截断，读取长度。
- Tag：增加、删除、列出（只列出可见的命名空间）。
- 查询：执行表达式，返回游标。

操作系统怎样把这些接口转给应用（handler、IPC 或其他方式）是操作系统的事，不在本工程内。

### 7.2 并发

- 读取在快照上进行，多个读者互不阻塞，也不阻塞写者。
- 写事务串行。是否支持多个写事务并发提交，留到有实测需求时再定。

## 8. 工程划分

Cargo workspace：

| crate | 内容 | 依赖 |
|---|---|---|
| `tagfs-core` | 对象、Tag、查询表达式、可见性规则、查询规划 | `no_std` + `alloc` |
| `tagfs-store` | 磁盘格式、写时复制 B+ 树、分配器、事务、回收、多设备 | `no_std` + `alloc`、`tagfs-core`、`tagfs-device` |
| `tagfs-device` | `BlockDevice` 接口、内存实现 | `no_std` + `alloc` |
| `tagfs-device-host` | 宿主机单文件、各平台裸盘 | `std` |
| `tagfs` | 对外 API，组合以上各层 | 以上全部 |
| `tagfs-tools` | mkfs、fsck、卷信息查看 | `std` |

核心三个 crate 不依赖 `std`，将来脱离宿主运行在裸机上时，只需要换设备实现。

测试从一开始就包括故障注入：在任意一次设备写入后模拟断电，重新挂载，检查卷一致、已提交的事务完整、未提交的事务不留痕迹。

## 9. 明确不做的

- 路径、目录、当前目录、相对位置。
- 硬链接、符号链接、挂载点。
- rwx 权限位、属主/属组、ACL。
- 任何 POSIX 或 Win32 文件语义，以及 FUSE、WinFsp 之类的挂载适配。
- 读取外部路径型文件系统（FAT、NTFS、ext4 等）。需要的话属于兼容层。

## 10. 待决定的问题

1. **多设备是否跨机器。** 对话里提到“设备 dev:a、dev:b 天然融合，离线的设备上的应用直接不可用”。如果这里的设备指不同的机器，TagFS 就是一个分布式文件系统，需要复制协议、一致性模型和网络传输，规模远大于单机多盘。建议：首版只做单机多盘，跨机器作为同一模型之上的后续一层。
2. **元数据放在哪里。** 单机多盘时，元数据树放在每块盘上各存一份（任一块盘离线都还能看到全部对象），还是分散存放（省空间，但设备离线时部分对象的身份和 Tag 也会丢失）。建议：全部元数据在每块盘上冗余保存，内容不冗余。
3. **版本历史。** 是否保留对象的历史版本，允许按版本读取。写时复制的结构天然支持，但会影响空间回收的规则。
4. **命名空间的书写规则。** “用户定义的必须是双长度，与系统的区分开（或者其他规则）”，具体规则要定下来。它只影响上层的字符串表示，核心按结构化类型处理。
5. **Tag 值类型清单。** 2.2 里的类型是否够用，是否需要浮点数、列表。
6. **删除的语义。** 删除一个对象时，指向它的引用 Tag 怎么处理：保留（成为悬空引用）、自动删除，还是拒绝删除。
7. **宿主目录后端。** 你的总结里列了 `dir://`（宿主机目录）后端。在本设计里，空间分配由 TagFS 自己负责，存放成一个宿主机单文件就够了；用目录存放等于把分配交回宿主文件系统。是否保留这个后端，要你定。
8. **静态加密、配额。** 首版是否需要。
